# データフロー — BQ公式データセットから何を抽出し、どう加工したか

デモ①（検索トレンド地域ビュー）のデータの出どころと加工の全体像。
カラム単位の詳細スキーマは [`data-dictionary.md`](./data-dictionary.md)、作成SQLの実体は
[`sql/create_region_view.sql`](./sql/create_region_view.sql) を参照。

---

## 全体図

```
【BQ公式データセット】bigquery-public-data.google_trends（全4テーブル・日次更新）
│
│  使うのは international_top_terms 1本だけ（残り3本はデモには不要）
│
└─ international_top_terms（2.05億行 / 16.5GB: 国別×地域×週の人気検索ワードTop25）
       │ 抽出: country_code = 'JP'（日本のみ）
       │       → 47都道府県 × 266週（2021-05-30〜）× 779語 ≈ 974万行
       │
       │ 加工①: 重複排除 — 同一(県,週,語)が複数 refresh_date で再掲されるため
       │         最新 refresh_date の観測値のみ採用
       │ 加工②: ゴミ除去 — score が NULL の複製行（全体の81.5%）を除外
       │         → 残った本物の観測 約178万行
       │ 加工③: 最新週フラグ付与 — is_latest_week（week = MAX(week)）
       │ 加工④: 順位の限定 — 元データの rank は98.2%が「最新順位の焼き付き」で
       │         履歴として信用できないため、最新週のみ latest_rank として保持
       │         （過去週は NULL = 誤用を物理的に防ぐ）
       ▼
   jp_region_weekly（177.6万行・約100MB）★ダッシュボード・エージェントの主役
       ├─ Looker Studio「地域ビュー」＋ データエージェント jp_trends_demo
       │
       │ 集計: term×県 でランクイン週数を COUNT（score の代わりに県間・語間比較に使える実績指標）
       ▼
   jp_term_region_weeks（3.5万行）— 定番ワード・地元ワード（is_local_term）用の補助テーブル
```

作成先は `ci-ss4-develop.demo_google_trends`（US）。

## 1. 元データ: 公式データセットにあるテーブル（4本）

| テーブル | 行数 | サイズ | 中身 | 今回 |
|---|---|---|---|---|
| `international_top_terms` | 2.05億 | 16.5GB | 国別→国内地域の週次**人気**ワードTop25 | **✅ 抽出元** |
| `international_top_rising_terms` | 1.94億 | 17.6GB | 同・**急上昇**ワード（percent_gain 付き） | ❌ 不使用（下記） |
| `top_terms` | 4,400万 | 3.2GB | 米国DMA（約210メディア圏）別・人気 | 使わない |
| `top_rising_terms` | 4,400万 | 3.4GB | 米国DMA別・急上昇 | 使わない |

- 更新: **日次更新が継続中**（最新週は2〜3週遅れ程度で追加）。OSMと違い鮮度の心配なし。
- 急上昇テーブルを使わない理由: 日本分は **percent_gain が47都道府県すべて同値（全国一律）**で、
  「地域で絞る」ビューでは県次元が無意味なため。急上昇的な見せ方は score の伸び（4週前比）で近似する。

## 2. 抽出したもの（条件と規模）

| 項目 | 内容 |
|---|---|
| 抽出条件 | `WHERE country_code = 'JP'` のみ |
| 生の規模 | 47都道府県 × 266週（2021-05-30〜2026-06-28）× 779語 ≈ **974万行** |
| 加工後 | 重複排除＋NULL除去で **177.6万行**（元の18.5%が本物の観測） |

## 3. 生データの"クセ"と対応（実データ検証で確定）

| # | クセ | 実測 | 対応 |
|---|---|---|---|
| 1 | refresh_date の重複再掲 | 同一(県,週,語)が複数 refresh_date で再掲、値も異なり得る | 最新 refresh_date のみ採用 |
| 2 | NULLスコアの複製ゴミ | 全体の **81.5%** が score=NULL（現在語を過去週へ複製した空行） | `score IS NOT NULL` で除外 |
| 3 | score は自己正規化 | 各(県×語)系列が自分のピーク=100（全35,489系列が100到達） | **大小比較は語間・県間とも不可**。scoreは同一系列の時系列（タイミング）専用。比較は latest_rank と「ランクイン週数・県数」（Top25入りの実績＝検索量ベース）で行う |
| 4 | rank の焼き付き | (県×語)の **98.2%** で rank が全週一定（最新順位のコピー） | 履歴 rank は破棄。最新週のみ `latest_rank` として保持 |
| 5 | 地域差が小さい | 人気語の77%が全47県に出現 | 地図は主役にしない（県選択の入口に限定） |

> 絶対的な検索ボリュームは取得不可（Google Trends は実数非公開）。デモは「量」ではなく
> **「タイミング（いつ盛り上がったか）」と「顔ぶれ（定番/今週/地元ワード）」**で見せる。

## 4. 作ったテーブル（2本）と加工内容

| テーブル | 行数 | 加工・集計 | 用途 |
|---|---|---|---|
| `jp_region_weekly` | 177.6万 | 上記クセ対応①〜④。元データからそのまま5列（region_name / region_code / week / term / score）＋加工付与2列（`is_latest_week` / `latest_rank`） | **地域ビューの全ページ**＋エージェント `jp_trends_demo` |
| `jp_term_region_weeks` | 3.5万 | term×県で**ランクイン週数**を集計（SQL: [`sql/create_term_region_weeks.sql`](./sql/create_term_region_weeks.sql)）。share（県シェア）と is_local_term（地元ワード判定: 計20週以上＋トップ県シェア30%以上、**該当27語**）を付与 | 定番・**地元ワード**ブロック＋エージェントの県間比較（score が県間比較に使えないため、この実績指標で代替） |

| 旧テーブル | 状態 |
|---|---|
| `jp_top_terms` / `jp_top_rising_terms` | 旧curated。エージェントは2026-07-03に新テーブルへ移行済み＝未参照 |

## 5. なぜこの形にしたか（設計判断のメモ）

- **1テーブル完結**: 旧設計は curated 2本＋dash 4本の6本構成だったが、rank焼き付き・NULL複製の
  問題を内包したまま集計していた。クセを構築時に一括で潰した1本に集約し、ダッシュボードも
  エージェントも同じテーブルを見る形にした（数字の食い違いが起きない）。
- **latest_rank を「最新週のみ」にした**: 過去週の順位を NULL にしておけば、Looker でもエージェントでも
  「過去のランキング」という嘘の見せ方が**構造的にできなくなる**。
- **急上昇テーブルを捨てた**: 県別に意味のある差が無いため。「急浮上」は score の4週前比で近似し、
  近似であることをエージェントが自分で説明するよう用語集に織り込んだ。
- **更新**: 元データは日次更新のため、`create_region_view.sql` を再実行（CREATE OR REPLACE・冪等）すれば
  最新週まで取り込める。スケジュールクエリ化する場合も同SQLをそのまま使える。
